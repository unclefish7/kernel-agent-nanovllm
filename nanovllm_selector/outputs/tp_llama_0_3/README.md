# 无桥接 MI100 上的 Llama 多卡推理

2026-11-19，在物理 GPU 0–3 上测试已生成的 `iter_llama4/attempt_4.py` 和 Llama-3.2-1B 权重。TP（张量并行）让每张卡承担同一层的一部分计算。当前机器上，给推理进程设置 `NCCL_P2P_DISABLE=1`，双卡和四卡都能在几十毫秒内续写一个词元（token）。单条短请求的延迟仍以单卡最低。

## 同一候选与输入的耗时

每次进程启动真实 nano-vLLM 引擎，使用 256 的上下文上限、单条请求、128 个输入词元，每条请求生成 4 个词元。首词时间包含处理整段提示的时间，续写每步输入一个词元。启动包含模型装载和引擎预热，计时从构造引擎开始。第二条请求改变首词，两条提示都短于一个缓存块。测试进程串行运行。

| 物理卡 | 通信路径 | 启动（秒） | 第二条请求首词（毫秒） | 已完成续写步中位数（毫秒） | 续写采样数 |
| --- | --- | ---: | ---: | ---: | ---: |
| 0 | 单卡 | 5.93 | 29.5 | 27.3 | 6 |
| 0、1 | 默认，卡间直接通信 | 12.31 | 7,680 | 7,756 | 6 |
| 0、1 | 经主机共享内存 | 12.42 | 39.6 | 36.2 | 6 |
| 0–3 | 默认，卡间直接通信 | 13.75 | 31,494 | 30,688 | 4 |
| 0–3 | 经主机共享内存 | 13.43 | 40.2 | 33.8 | 6 |

四卡默认路径完成了第一条请求。第二条请求又返回首词和一个续写词元后，进程达到 220 秒时限。表中只计入已返回的步骤。四卡共享内存路径完成了两条请求。独立新进程又复测了一次四卡共享内存路径，续写中位数为 33.9 毫秒。测量范围是单请求延迟。

## 为什么一个词元要等几秒

这个 Llama 有 16 层，每层有两次跨卡求和，输入嵌入还要再求和一次。每个续写步总共需要 33 次求和，每次每张卡只提供 4,096 字节，最后还要把各卡的词表分数收集到主卡。后一层依赖前一层的结果，这些等待会累加。

在独立的数值验收中，对第二个续写步记录主卡计算流上各次通信前后的设备时间。这一时间包括其他卡到齐和通信完成前的等待，不能直接换算为链路带宽。

| 实测路径 | 整步（毫秒） | 33 次求和累计（毫秒） | 单次求和中位数（毫秒） | 最后收集（毫秒） |
| --- | ---: | ---: | ---: | ---: |
| 双卡默认 | 7,628.4 | 7,371.8 | 221.82 | 219.66 |
| 双卡共享内存 | 36.9 | 9.7 | 0.25 | 0.26 |
| 四卡共享内存 | 39.1 | 11.6 | 0.35 | 0.30 |

双卡默认路径中，等待这 34 次通信占整步约 99.5%。AMD 的跨卡通信库 RCCL 在默认路径日志中记录 `via P2P/IPC`，切换后记录 `via SHM/direct/direct`。使用相同的卡、权重和计算代码，只改变通信路径，就复现了秒级与毫秒级的差异。PCIe（卡与主机之间的互连）或驱动内部具体哪一环产生了约 220 毫秒的等待，本次没有进一步区分。该开关只设置在测试进程中。[AMD RCCL 配置说明](https://rocm.docs.amd.com/projects/rccl/en/latest/how-to/rccl-usage-tips.html)

## 生成结果与参考模型的差异

用项目的 `port.evaluate` 对照 Hugging Face 原模型。输入长度 128，两次处理提示得到两份首词分数，再使用引擎实际生成的词元续写两步，共比较四份完整词表，每份 128,256 个分数。双卡默认、双卡共享内存、四卡共享内存均为 4/4 首选词相同，最大绝对分差均为 0.1875。最低余弦相似度（衡量整份分数的接近程度）双卡为 0.999810，四卡为 0.999916。这些结果通过项目的近似验收。单卡逐项相等的验收结果在 [verified.json](../iter_llama4/verified.json)。

## 复现

本次版本为 PyTorch 2.12.0+rocm10.0.0、RCCL 2.30.4。宿主机 `rocm-smi` 报告的物理 GPU 0、1、2、3 总线号依次是 `03`、`27`、`43`、`63`。此容器中的设备顺序不同，下面的可见性设置将这四张卡按物理顺序传给引擎。测量脚本会在加载权重前核对 PCI 地址。

```bash
docker exec -w /workspace \
  -e HIP_VISIBLE_DEVICES=2,3,1,0 -e NCCL_P2P_DISABLE=1 \
  -e OMP_NUM_THREADS=4 -e MKL_NUM_THREADS=4 nanovllm-selector-rocm-dev \
  python -B -m nanovllm_selector.bench_tp \
  --model tmp/models/llama-3.2-1B \
  --candidate nanovllm_selector/outputs/iter_llama4/attempt_4.py \
  --buses 0000:03:00.0,0000:27:00.0,0000:43:00.0,0000:63:00.0 \
  --report nanovllm_selector/outputs/tp_llama_0_3/local_tp4.json
```

双卡使用 `HIP_VISIBLE_DEVICES=2,3` 和前两个 PCI 地址。复现默认通信路径时，移除进程的 `NCCL_P2P_DISABLE` 设置，慢路径可用 `--requests 1` 限制请求数。复现通信等待计时可用同目录的 `profile_step.py`，通过 `python -B -m nanovllm_selector.outputs.tp_llama_0_3.profile_step` 运行。给它设置 `TP_EXPECT_BUSES` 为相同的地址列表，传入 `port.evaluate` 的参数 `--model`、`--candidate`、`--tp`、`--lengths 128 --decode-steps 2 --no-exact --report <路径>`。

同目录的 `tp*.json` 保存计时，`tp4.partial.json` 由当时的逐步日志提取，`accuracy*.json` 保存数值对照。运行日志 `*.log` 保存在本机，可用 `rm -f nanovllm_selector/outputs/tp_llama_0_3/*.log` 清理。
